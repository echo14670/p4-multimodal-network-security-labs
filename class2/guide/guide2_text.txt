第二次实验指导：模态调度与异构封装
实验主题：基于 P4 的多模态网络内生安全
前置条件：已跑通原始三模态 Demo，并创建 class1-baseline tag
本次实验在原始 Demo 的 IPv4、IPv6 和 Source Routing 三条路径上继续开发：主机只发送一份实验报文，源网关在网络内
部复制三份，再分别使用三种外层协议进入不同路径。本次先完成调度、复制、封装和路径验证；目的网关的多数裁决在下
次实验继续完成。
第一部分：实验内容与任务
1.1 必要概念
1. 模态与异构转发
本实验把一种协议头、一套转发规则和一条网络路径组成的转发方式称为一个“模态”。IPv4 根据 IPv4 目的地址转发，
IPv6 根据 IPv6 地址转发，Source Routing 则由报文携带路径信息。三种模态使用不同的协议头和路径，因此可以对同一份
数据提供多个相互独立的转发结果。
2. 源网关、目的网关与方向
源网关是主机报文进入多模态网络的第一台网关交换机，负责识别实验流量、复制报文并进行异构封装。目的网关是多条路
径的汇聚点，后续负责比较各模态结果并恢复原始报文。
网关角色会随通信方向互换：同一台网关在一个方向可能负责调度，在反向则可能负责汇聚结果。报文内需要保留方向信
息，以便网关选择正确的处理分支。
3. 内层报文、外层报文与封装
主机原本发送的 IPv4 报文称为“内层报文”。源网关为它加上 IPv4、IPv6 或 Source Routing 头，得到用于网络内部转发
的“外层报文”，这个过程称为封装。目的网关删除网络内部的外层信息，恢复主机原本报文的过程称为解封装。
主机可以使用 UDP 或 TCP 传输实验数据。两种方案的多模态处理思路相同，但 Parser、CRC 字段范围和收发脚本必须与实
际选择的传输层协议一致。
4. PolyShim 与受保护数据
PolyShim 是放在外层模态头和内层报文之间的实验协议头。它保存报文方向、序号、模态编号、入口校验值和内层协议类
型，使三种外层报文可以使用同一套后续处理逻辑。
protected_data 是为了便于 Parser 提取和完整性比较而定义的定长实验数据。固定长度使 Parser 能够按确定位宽提取字
段，不代表 P4 可以随意读取任意长度的应用层负载。
5. 报文序号与 CRC32
sequence_number 是源网关为每份原始实验报文分配的序号。一份原始报文复制出的三份副本使用同一序号，目的网关才能
知道它们属于同一组。
CRC32 把若干报文字段计算为一个 32 位校验值。source_crc32 是源网关在报文进入多模态路径前计算的参考值，后续可用
来检查指定字段是否发生变化。CRC32 用于实验中的错误检测，不是密码学认证方法。
6. Parser、Ingress、PRE 与 Egress
· Parser 按协议格式从报文中提取 header，为后面的表和 action 提供字段。
· Ingress 是入口处理流程，负责识别报文、查表、准备关联信息并触发复制。
· PRE（Packet Replication Engine）是 v1model 中的报文复制模块，它根据控制器配置的 multicast group 产生多个
副本。
· Egress 是每个副本离开交换机前的处理流程，可以根据已确定的出口选择外层封装。

1.2 实验内容
在原始三模态 Demo 上增加模态调度逻辑。实验报文从 h1 或 h2 发出后，源网关识别该报文，生成用于关联副本的信息，

4. 异构封装与路径转发：为三份副本生成不同的外层协议头，使其进入 IPv4、IPv6 和 Source Routing 路径。
5. 结果验证与原有功能检查：证明“一份输入、三份副本、三种封装、三条路径”，并确认原始 Demo 中已跑通的功能
仍然正常。

第二部分：实验过程及要求
每组继续使用原团队 Git 仓库，可以使用 代码/调度开发骨架/ 开始，也可以将其中新增的脚本和 TODO 合并到本组代码。具
体的表名、action 拆分方式、multicast group 编号和代码组织可由小组自行设计；下文给出的编号和端口是与材料骨架配
套的参考方案。
2.1 Parser 功能完善
Parser 需要为两类报文提供清晰的解析路径：
· 来自主机的原始实验报文；
· 携带 IPv4、IPv6 或 Source Routing 外层的多模态副本。
解析结果应能让后续 control 访问外层模态头、PolyShim、内层 IPv4、所选传输层头和定长实验数据。材料参考报文使用
16 字节数据，短消息补零，编码后超过 16 字节则拒绝发送。如果选择 UDP，可参考材料中目的端口 5000 的识别方式；如
果选择 TCP，需要考虑 TCP dataOffset 和可选项对负载起始位置的影响。实验中可以由发送脚本构造无 TCP options 的固
定格式报文，同时在报告中说明适用范围。
新增解析分支不应改变普通 ARP、ping、IPv6 和原 Source Routing 报文的处理结果。
2.2 入网报文识别与关联信息生成
源网关需要区分“需要调度的实验报文”和“按原有方式转发的普通报文”。可以组合使用入端口、IP 地址、传输层协议号
和端口，也可以提出其他能清楚区分流量的方案。在材料拓扑中，h1→h2 时 S1 是源网关、S2 是目的网关；h2→h1 时角色
互换。正向和反向报文应能得到正确的方向和网关角色。
序号和入口 CRC 需在报文复制前生成，这样三份副本才能共享同一组关联信息。CRC 可覆盖内层 IP 地址、协议号、传输层
端口和定长数据等稳定字段；具体范围可结合小组方案确定，但入口和目的网关必须使用同一顺序、同一宽度重新计算。
TTL、外层地址和逐跳变化的字段不适合放入跨路径比较范围。

2.3 报文复制与模态调度
材料的参考方案在 S1 和 S2 配置 multicast group 10，并使用下列副本映射：
(出口端口 2, 副本编号 1)
(出口端口 3, 副本编号 2)
(出口端口 4, 副本编号 3)
Ingress 命中调度条件后设置 multicast group，PRE 再根据本机的 group 配置复制报文。S1 和 S2 的 PRE 状态相互独立，
所以反向流量也需要对应配置。
小组可以继续使用 group 10，也可以使用其他 group 编号或等价的 P4Runtime 组织方式。验证时需要能从控制器配置和出
口报文中看出“一份原始输入在源网关内部复制”，不能由主机分别构造三份模态报文代替。
2.4 异构封装与路径转发
副本进入 Egress 时，PRE 或流量管理模块已经确定 standard_metadata.egress_port。P4 程序可读取该字段选择封装，无需
在 Egress 重新决定出口。与材料拓扑配套的参考映射为：
egress_port modality_id 外层封装
2 1 IPv4，protocol=253
3 2 IPv6，nextHdr=253
4 3 Source Routing，EtherType=0x1234
如果小组调整了端口、模态编号或外层标识，需要同步调整拓扑、控制器、P4 处理和验证记录，让各部分可以互相印证。
三份副本的 sequence_number 应保持一致，modality_id 用来区分它们所属的模态。
2.5 结果验证与原有功能检查
验证应回答以下问题：
1. 发送端是否只生成一份原始实验报文？
2. 三份副本是否由源网关复制，并携带相同序号？
3. 三份副本是否具有不同的模态编号和外层协议头？
4. 关键端口的 pcap 或交换机日志是否能说明三条真实路径？
5. 新增功能后，原始 Demo 的 IPv4、IPv6、ARP 和 Source Routing 功能是否仍然正常？
证据形式可以根据小组的调试方式选择，但应保留足以定位报文、模态和路径的命令、pcap、日志或截图，不建议只使用
一张终端收包图作为全部证据。
