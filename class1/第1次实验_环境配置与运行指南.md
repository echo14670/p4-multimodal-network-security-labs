## 二、PDF 核心内容解释
- 三种“模态”：同一逻辑数据用不同协议与路径承载——IPv4 走 `h1-s1-s11-s12-s2-h2`；IPv6 走 `h1-s1-s21-s22-s2-h2`；Source Routing 由数据包自带端口栈逐跳选路，走 `h1-s1-s31-s32-s2-h2`。`s41/s42` 本轮无对应流量。
- SR 端口栈（正向/反向）：`h1->h2: 4 2 2 1`，`h2->h1: 4 1 1 1`。注意旧说明的 `3 2 2 1` 会误入 IPv6 蓝色路径，不能作为绿色路径证据。
- P4 数据流五阶段：MyParser（按 EtherType 分派 IPv4/IPv6/ARP/SR）→ MyIngress（SR 弹端口栈、IPv4/IPv6 查表、ARP 回包）→ MyEgress（本轮为空，是后续扩展点）→ MyComputeChecksum → MyDeparser（按 header validity 发头）。
- 控制器职责：`mycontroller.py` 为 10 台交换机装 pipeline 并下发 IPv4/IPv6 表项；SR 不依赖控制器。**控制器前 pingall 失败、控制器后成功是预期现象**。
- 路径证据：pingall 只能证明端到端，必须用 pcap/交换机日志证明实际链路（s11/s12、s21/s22、s31/s32 各自独立）。
- 运行环境纪律：`source ~/p4setup.bash` 仅在命令找不到时执行；不 `apt upgrade`、不重装 p4c/BMv2/PI/gRPC/Mininet；demo 使用项目自带 `utils/`，不覆盖 `~/tutorials/utils`；材料复制后出现 `^M`/无执行权限时用 `dos2unix`、`chmod +x`。
- 完成标准（详见 PDF）：basic 0% dropped；控制器后 IPv4/IPv6/SR 双向通过且 SR 用正确绿色端口栈；pcap 结论与 topology 一致；clean 后可重跑；组队登记；第 1 次进度截图；Git tag `class1-baseline`。

4. Scapy 与 SR 路径：

## 六、常见问题与本机特有风险
- **VM 无法启动，报 VT-x/WHPX 不可用**：本机开启了 VBS/内存完整性（家庭版可能无 Windows Hypervisor Platform）。先以管理员 PowerShell 执行 `dism /online /Get-FeatureInfo /FeatureName:HypervisorPlatform` 查看状态；若功能存在但未启用，`dism /online /enable-feature /featurename:HypervisorPlatform /all /norestart` 后重启；若家庭版不支持，则到“设置 → Windows 安全中心 → 设备安全性 → 核心隔离”关闭“内存完整性”后重启。备选：PDF 官方复测流程在 VMware 完成，VirtualBox 持续冲突时可考虑 VMware。
- `p4c`/`simple_switch_grpc` 找不到 → 执行 `source ~/p4setup.bash`（不要重装工具链）。
- gRPC/Thrift 端口占用 → `make stop`、`make clean`，必要时 `pgrep -a -f simple_switch` 清理残留进程。
- 换 Ubuntu 软件源 → 仅选 Ubuntu 24.04（noble）配置，非必需步骤。
- demo 行为与其他成员不一致 → 核对镜像日期（2026-Aug-01）、架构、项目 commit 与本地 `utils` 是否一致。
